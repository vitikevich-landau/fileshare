# Техническое задание: файлообменник на C++20

Рабочее название: **fileshare** (клиент-серверный, не P2P — см. п.1.3)

---

## 1. Назначение и цели

### 1.1 Что это
Консольное серверное приложение, которое раздаёт заранее указанные файлы по сети, и консольное клиентское приложение, которое видит список доступных файлов и может их скачать. Список раздаваемых файлов сохраняется между перезапусками сервера.

### 1.2 Учебные цели проекта
- Бинарный протокол поверх TCP (framing, сериализация без "магии" через reinterpret_cast)
- Concurrency на реальной задаче: много клиентов, каждый качает независимо
- Персистентное состояние на диске (JSON-конфиг между запусками)
- Устойчивость к обрывам связи, некорректным данным, гонкам
- Прямое продолжение архитектуры epoll + thread pool, которую отрабатываем на "Таверне"

### 1.3 Важное уточнение по терминологии
Это **не BitTorrent**. В настоящем торренте клиенты раздают куски файла друг другу (P2P swarm), а трекер только помогает найти пиров. Здесь всё проще и честнее: один сервер — источник истины, клиенты только скачивают с него. Архитектурно это ближе к FTP со своим протоколом. P2P-раздача между клиентами — сознательно вне scope (см. п.11).

## 2. Общая архитектура

```
┌─────────────────┐         TCP, свой бинарный протокол        ┌─────────────────┐
│  Client #1       │ ───────────────────────────────────────►  │                  │
│  (консоль)        │ ◄───────────────────────────────────────  │     Server       │
└─────────────────┘                                              │   (консоль)      │
┌─────────────────┐                                              │                  │
│  Client #2       │ ◄──────────────────────────────────────►   │  ┌────────────┐  │
│  (консоль)        │                                              │  │config.json │  │
└─────────────────┘                                              │  │(shared files)│ │
        ...                                                       │  └────────────┘  │
┌─────────────────┐                                              │  ┌────────────┐  │
│  Client #N       │ ◄──────────────────────────────────────►   │  │ share/*.*  │  │
└─────────────────┘                                              │  └────────────┘  │
                                                                    └─────────────────┘
```

Компоненты:
- **Server** — процесс с консольным admin-интерфейсом (свой поток) + сетевой движок (epoll + thread pool, свои потоки). Хранит каталог раздаваемых файлов в `config.json`.
- **Client** — процесс с консольным интерфейсом. Подключается к одному серверу за раз, может слушать список файлов и качать один или несколько параллельно (если решишь поддержать).
- **Протокол** — свой бинарный, поверх голого TCP. Не JSON/HTTP (см. предыдущее обсуждение — тут это осознанный выбор ради учебной цели, а не что-то от лени).

Почему TCP, а не UDP: здесь критична гарантированная доставка байт файла и порядок, а не задержка — обратная ситуация тому, что обсуждали для игрового сервера.

## 3. Функциональные требования

### 3.1 Сервер — консольные команды

| Команда | Описание |
|---|---|
| `add <path> [alias]` | Добавить файл в раздачу. Если `alias` не указан — берётся имя файла. Считается SHA-256, всё сохраняется в `config.json`. |
| `remove <alias>` | Убрать файл из раздачи (сам файл на диске не трогаем). |
| `list` | Показать текущий каталог раздачи: alias, размер, checksum. |
| `clients` | Показать подключённых клиентов: адрес, что качает, сколько байт передано. |
| `kick <client_id>` | Принудительно оборвать соединение с клиентом. |
| `status` | Аптайм, суммарно отданных байт, число завершённых закачек. |
| `shutdown` | Graceful остановка: перестать принимать новые подключения, дождаться текущих закачек (с таймаутом), выйти. |
| `help` | Список команд. |

Требование: admin-консоль должна оставаться отзывчивой, пока сервер обслуживает клиентов — она не должна блокироваться сетевым кодом (см. п.6, это то же самое "parallel admin control", что уже реализовано в ATM-проекте).

### 3.2 Клиент — консольные команды

| Команда | Описание |
|---|---|
| `connect <host> <port>` | Подключиться к серверу. |
| `list` | Запросить и показать список доступных файлов (alias, размер, checksum). |
| `download <alias> [as <path>]` | Скачать файл, показывать прогресс (% или МБ/МБ). |
| `cancel` | Прервать текущую закачку. |
| `status` | Текущий прогресс, если идёт закачка. |
| `disconnect` | Закрыть соединение с сервером. |
| `help` | Список команд. |

### 3.3 Пример сценария

```
# Сервер
$ ./fileshare_server --port 5555
> add /home/viktor/share/ubuntu-24.04.iso
Добавлено: ubuntu-24.04.iso (4.5 GiB), sha256 посчитан
> list
ubuntu-24.04.iso   4.5 GiB   e3b0c442...

# Клиент, с другой машины
$ ./fileshare_client
> connect 91.211.xx.xx 5555
Подключено.
> list
1) ubuntu-24.04.iso   4.5 GiB
> download ubuntu-24.04.iso
Качаю... 34% (1.5 GiB / 4.5 GiB)
Готово. Checksum совпал.
```

## 4. Протокол обмена данными

### 4.1 Формат фрейма

Каждое сообщение — заголовок (5 байт) + payload:

```
 0        1        2        3        4        5 ...
┌────────┬────────────────────────────────────┬─────────────┐
│msg_type│         payload_length (u32)         │   payload   │
│ 1 байт │           4 байта, big-endian         │  N байт     │
└────────┴────────────────────────────────────┴─────────────┘
```

Сериализация — явными функциями, а не `reinterpret_cast` структуры целиком:

```cpp
// Почему НЕ packed struct + reinterpret_cast на весь буфер:
// padding между полями не гарантирован стандартом одинаковым на всех платформах,
// а cast байтового буфера на struct* — strict aliasing UB.
// Пишем/читаем поля явно, по одному — надёжно и видно, что происходит.

void write_u8 (std::vector<uint8_t>& buf, uint8_t  v);
void write_u16be(std::vector<uint8_t>& buf, uint16_t v);
void write_u32be(std::vector<uint8_t>& buf, uint32_t v);
void write_u64be(std::vector<uint8_t>& buf, uint64_t v);

uint16_t read_u16be(const uint8_t* p);
uint32_t read_u32be(const uint8_t* p);
uint64_t read_u64be(const uint8_t* p);
```

### 4.2 Типы сообщений

```cpp
enum class MessageType : uint8_t {
    LIST_REQUEST     = 0x01,  // client -> server
    LIST_RESPONSE    = 0x02,  // server -> client
    DOWNLOAD_REQUEST = 0x03,  // client -> server
    CHUNK_DATA       = 0x04,  // server -> client (много раз подряд)
    DOWNLOAD_DONE     = 0x05,  // server -> client
    ERROR             = 0x06,  // любое направление
    PING              = 0x07,  // client -> server
    PONG              = 0x08,  // server -> client
};
```

| Сообщение | Payload |
|---|---|
| `LIST_REQUEST` | пусто |
| `LIST_RESPONSE` | `entry_count: u32`, затем для каждого файла: `alias_len: u16` + `alias`, `size: u64`, `sha256: 32 байта` |
| `DOWNLOAD_REQUEST` | `alias_len: u16` + `alias`, `offset: u64` (0 = с начала, >0 = докачка) |
| `CHUNK_DATA` | сырые байты файла, до `CHUNK_SIZE` за раз (длина — это и есть `payload_length` из заголовка) |
| `DOWNLOAD_DONE` | `sha256: 32 байта` — checksum всего файла из каталога, клиент сверяет с посчитанным локально |
| `ERROR` | `code: u16`, `message_len: u16` + `message` |
| `PING` / `PONG` | пусто |

Сценарий закачки: один `DOWNLOAD_REQUEST` → сервер шлёт N `CHUNK_DATA` подряд, пока не дойдёт до конца файла → один `DOWNLOAD_DONE`.

### 4.3 Ограничения размеров

| Константа | Значение | Зачем |
|---|---|---|
| `MAX_ALIAS_LEN` | 255 байт | защита от абсурдных имён |
| `MAX_CONTROL_PAYLOAD` | 1 MiB | верхняя граница для `LIST_RESPONSE`/`ERROR` — если пришло больше, это либо баг, либо атака, соединение рвём |
| `CHUNK_SIZE` | 64 KiB (настраивается) | размер одного `CHUNK_DATA` |

### 4.4 Контроль целостности
SHA-256 всего файла считается один раз при `add` и хранится в `config.json` — не пересчитывается на каждую раздачу. Библиотека: OpenSSL (`libssl-dev`, EVP API) — реалистичный вариант, заодно опыт линковки внешней crypto-библиотеки. Если не хочется тащить зависимость на старте — можно временно на CRC32 (легко написать самому), но это не защищает от намеренной подмены, только от случайной порчи; апгрейд на SHA-256 сделать позже.

## 5. Персистентность

`config.json` рядом с исполняемым файлом сервера:

```json
{
  "version": 1,
  "shared_files": [
    {
      "alias": "ubuntu-24.04.iso",
      "path": "/home/viktor/share/ubuntu-24.04.iso",
      "size_bytes": 4881539072,
      "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b85"
    }
  ]
}
```
Загружается при старте сервера, перезаписывается при каждом `add`/`remove`. Используем nlohmann/json — то же, что и в ATM-проекте.

## 6. Модель параллелизма

Сервер = reactor (epoll) + пул воркеров, ровно та архитектура, к которой идём по шагам на "Таверне":
- Один (или несколько) поток крутит `epoll_wait`, отслеживает готовность сокетов
- Реальная работа (чтение файла с диска, запись в сокет) уходит в thread pool через очередь задач — тот же паттерн очереди, что уже реализован в ATM-симуляторе, только источник задач — сеть, а не консоль
- Admin-консоль сервера — отдельный поток, читающий stdin, кладущий команды в свою потокобезопасную очередь; сетевой движок эту очередь периодически вычитывает. Это и есть "parallel admin control" из ATM, применённый повторно

## 7. Обработка ошибок и граничные случаи

- Запрошен несуществующий `alias` → `ERROR FILE_NOT_FOUND`
- Клиент отваливается посреди закачки (`recv() == 0` или `ECONNRESET`) → сервер освобождает файловый дескриптор и слот воркера, **не падает**
- Битый/противоречивый фрейм (неизвестный `msg_type`, `payload_length` больше лимита) → соединение с этим клиентом рвём, остальных не трогаем
- `offset` в `DOWNLOAD_REQUEST` больше размера файла → `ERROR UNSUPPORTED_OFFSET`
- Частичная запись/чтение сокета (short read/write) — всегда в цикле, никогда не считаем что `send`/`recv` за один вызов передаёт весь буфер целиком
- Файл убрали из раздачи (`remove`), пока кто-то качает — задокументировать явно выбранное поведение (проще всего: уже начатая закачка доигрывается, т.к. `open()`-нутый fd в Linux остаётся валиден даже после удаления/`remove` из каталога)

## 8. Нефункциональные требования

- **Язык**: C++20, не ниже, без исключений (можно и с ними — на твой вкус)
- **Сборка**: CMake ≥ 3.20, флаги `-std=c++20 -Wall -Wextra -Wpedantic`, ноль варнингов
- **Зависимости**: nlohmann/json (конфиг), OpenSSL (checksum), GoogleTest (тесты) — всё уже знакомо по ATM-проекту
- **Тесты**: GoogleTest на сериализацию/десериализацию протокола — это чистая логика без сети, тестируется легко и в первую очередь
- **Sanitizers**: ASan обязателен на этапе разработки, TSan — как только появляется epoll+thread pool
- **Логи**: временная метка + уровень (INFO/WARN/ERROR) в stdout, без переусложнения на первых этапах

## 10. Этапы разработки

Прямое переиспользование плана с "Таверной" — тот же путь, но с реальной пользой на выходе.

| Этап | Что делаем | Соответствует |
|---|---|---|
| **M0** | Протокол и конфиг без сети: сериализация фреймов + JSON load/save, юнит-тесты | — |
| **M1** | Blocking-сервер на 1 клиента: `LIST` + `DOWNLOAD` одного файла работают end-to-end | Шаг 1 (echo-сервер) |
| **M2** | Thread-per-connection: несколько клиентов качают одновременно, admin-консоль в отдельном потоке | Шаг 2 |
| **M3** | Нагрузочный тест: скрипт поднимает N параллельных закачек, смотрим где упирается thread-per-connection | Шаг 3 |
| **M4** | Переход на epoll + thread pool | Шаги 4–5 |
| **M5** | Устойчивость: битые фреймы, обрывы связи, `kick`, graceful `shutdown` | — |
| **M6** (стретч) | Докачка по `offset`, переписать event loop на C++20 coroutines | Шаг 7 |

## 11. Осознанно вне scope

- Настоящий P2P между клиентами (то, что делает торрент торрентом) — DHT, piece-selection, choking/unchoking
- Шифрование трафика (TLS) — можно накрутить поверх TCP позже, но не часть основного ТЗ
- Аутентификация/авторизация — все клиенты анонимны и равноправны
- NAT traversal — предполагается публичный IP или проброшенный порт (как на Timeweb Cloud)
- GUI — только консоль с обеих сторон
