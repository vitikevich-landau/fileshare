# M3 — нагрузочный тест thread-per-connection

Дата: 2026-07-13. Инструмент: [`fileshare_loadtest`](../src/loadtest_main.cpp) + [`scripts/loadtest.sh`](../scripts/loadtest.sh).

## Стенд

- **Сервер** (M2, thread-per-connection) и клиенты — на одной машине, через loopback (`127.0.0.1`).
- Docker/Linux, **6 CPU**, сборка **Release** (без санитайзеров).
- Клиент качает файл в память и **отбрасывает** байты после сверки CRC — меряем пропускную способность сервера+сети, а не диск клиента. Файл лежит в page cache сервера, так что сервер не упирается в диск.
- N параллельных клиентов, каждый качает файл `repeats` раз подряд по одному соединению.

## Выводы

1. **Масштабируется по числу ядер.** До N ≈ числа CPU (6) агрегатная пропускная способность растёт почти линейно и достигает пика (~1.6 ГБ/с при N=6).
2. **Плато после числа ядер.** При N > 6 агрегат не растёт (болтается ~1.1-1.5 ГБ/с), а per-client throughput падает ∝ 1/N — клиенты просто делят фиксированный ресурс.
3. **Накладные расходы потоков видны, но коллапса нет.** Разброс агрегата растёт с N (context-switching между десятками-сотнями потоков на 6 ядрах), но **сервер корректно обслужил все 128 одновременных соединений (128/128)** — ни падения, ни потери данных.
4. **Узкое место — потоки и CPU, не сеть.** Один поток на соединение + блокирующий I/O: при сотнях соединений это сотни потоков, большинство из которых простаивают в `recv`/`send`. На реальном сервере с тысячами медленных клиентов это не масштабируется (память под стеки, планировщик).

### Оговорки
- Loopback + один хост: клиент и сервер делят те же 6 ядер, клиентский CRC конкурирует с отдачей сервера — абсолютные МБ/с занижены/зашумлены. **Важна форма кривой, а не абсолют.**
- Все соединения активны и быстры. Настоящая боль thread-per-connection — **много одновременных, но медленных/простаивающих** клиентов (поток на каждого), чего loopback-тест не воспроизводит.

## → Мотивация M4

Перейти на **epoll + thread pool**: небольшой фиксированный пул потоков (≈ число ядер) обслуживает тысячи соединений событийно, без потока на каждое. Ожидаем: тот же пик пропускной способности при малом N, но без роста числа потоков и деградации/разброса при большом числе (особенно простаивающих) соединений.

## M4 — epoll, тот же стенд (16 MiB, repeats=2)

| clients | M2 thread-per-conn MB/s | **M4 epoll MB/s** |
|--:|--:|--:|
| 1 | 309 | 307 |
| 4 | 1145 | 1274 |
| 8 | 1309 | 1449 |
| 16 | 1356 | **1723** |
| 32 | **846** (провал) | **1653** |
| 64 | 936 | **1723** |
| 128 | 1266 | 1356 |

**Вывод подтверждён:** epoll держит пик ~1.7 ГБ/с от N=16 до N=64 без провала на N=32, который был у thread-per-connection, и при этом использует **~6 воркеров вместо 128 потоков**. При N=128 обе версии проседают (клиентский CRC + сервер делят 6 ядер на loopback), но epoll стабильно выше и ровнее. Развязка «число соединений ≠ число потоков» достигнута.
